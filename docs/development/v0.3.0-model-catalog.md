## Inference and field capabilities

This matrix comes from pinned [V30](https://github.com/OliBomby/Mapperatorinator/blob/0e2b0e387aab4b35c64b0b11b12d47578dea7587/configs/train/v30.yaml), [V31](https://github.com/OliBomby/Mapperatorinator/blob/0e2b0e387aab4b35c64b0b11b12d47578dea7587/configs/train/v31.yaml), [V32-mini](https://github.com/OliBomby/Mapperatorinator/blob/0e2b0e387aab4b35c64b0b11b12d47578dea7587/configs/train/v32-mini.yaml), and [V32](https://github.com/OliBomby/Mapperatorinator/blob/0e2b0e387aab4b35c64b0b11b12d47578dea7587/configs/train/v32.yaml) training configs and their [inference configs](https://github.com/OliBomby/Mapperatorinator/tree/0e2b0e387aab4b35c64b0b11b12d47578dea7587/configs/inference). A conditioning token in a config **does not** establish Beatforge runtime support.

All pinned inference YAMLs default to BF16 and `generate_positions=false`, and reference an optional diffusion checkpoint. Beatforge should keep unmanaged checkpoints disabled. V30/V31 architectures and tokenizers differ from V32, so the V32 backbone shim and fast decoder workaround cannot be copied blindly. The worker must select config and compatibility handling by model ID, then measure BF16/FP32 fallback, memory, and output on supported GPUs.

## Extensible catalog and listing gate

- Each model has an immutable package ID, official repository, immutable revision, standard subfolder, file sizes/hashes, license evidence, training/inference config hashes, capability flags, acquisition mode, and acceptance status. `research_only` models cannot currently be installed or selected. After engineering and release acceptance, V30/V31 are planned for exact-version manual import only; V32-mini/V32 can be downloaded from upstream by the app. Future models arrive through an app update rather than following upstream `main` at runtime.
- Capability flags distinguish tested support, config evidence without runtime testing, and unsupported/disabled. Generate must disable or reject unsupported controls before submission, and the worker must reject them again. Writing a value into `.osu` alone does not prove model conditioning.
- Before listing a model, review license terms; hash downloaded weights; pass offline loading/health, one- and multi-difficulty generation, reference and field contracts, validation, osu! import, cancellation/retry, GPU resource recording, and V32 regression. Old jobs retain their exact model ID/version and never silently switch models.

## Open questions and release decisions

1. **V30/V31 weight terms are unclear and require a recorded release decision.** Their official model cards give no usable grant. The source repository's MIT license does not by itself establish the weights' terms. Beatforge cannot assign a license to upstream weights. The 0.3.0 plan lets users obtain them in a browser and manually import the exact hashed files; Beatforge will neither download nor mirror these weights. This avoids Beatforge distributing the weights but does not clarify upstream terms of use. Record this boundary and the release decision before enabling import; the models currently remain `research_only`.
2. **Some controls have no training signal in V30/V31.** V30 lacks descriptor conditioning; V30 and V31 lack target difficulty conditioning. Tasks 0.3-03 through 0.3-05 need clear input behavior and UI copy.
3. **Runtime compatibility is untested.** This research did not download large weights or perform GPU inference. V30/V31 backbones, TIMING reference behavior, V32-mini low-memory performance, and per-model default output need testing in 0.3-04/0.3-09.
