# Beatforge 0.3.0 development plan (scope draft)

[繁體中文](v0.3.0-plan.zh-TW.md) · [Developer documentation](README.md) · [0.2.0 plan](v0.2.0-plan.md)

Status: agreed direction; implementation and release date are not yet scheduled. Version 0.3.0 focuses on **managed model selection and generation-quality visibility**, while retaining osu!standard and the existing local generation, validation, history, and import flows.

## Scope

### 1. Validated model selection

- The 0.3.0 target catalog is **V30, V31, V32-mini, and V32**, with V32 remaining the default. Pin and review each added model's source revision, files, license, SHA-256, inference configuration, compatibility, and hardware results before declaring support. If a model is blocked, record the issue and resolve the release scope explicitly rather than silently dropping it.
- Users choose which models to download. Install, verify, repair, and remove each model independently. Select one installed osu!standard-compatible model per job. Show installation state, supported controls, and relevant hardware guidance. Do not accept arbitrary checkpoint paths.
- Use an extensible managed catalog: future upstream models can add their own ID, locked source, file inventory, capabilities, and acceptance record without rewriting the Generate UI or job data format. New models still require an application update and validation; do not automatically trust an upstream release at runtime.
- Persist the model package ID, version, and effective source in requests, history, retry/regeneration, and provenance. If the original model is unavailable, offer installation or a clear error; never silently substitute V32. Preserve V32 behavior for legacy jobs.
- Check descriptors, negative descriptors, reference maps, metadata, HP/OD/slider controls, precision, and defaults for each model. Block or explain unsupported combinations before submission, and isolate model-specific worker compatibility code.

### 2. Comparable runs and quality warnings

- Copy a historical job's song, difficulties, and effective settings while changing only the model. Keep both outputs and provenance. Compare at least model identity, elapsed time, validation warnings, object count, and distribution over time.
- Warn with a navigable time range for long gaps without new objects and unusually dense simultaneous objects. Use the known roughly 20-second gap in a 0.2.0 result as an investigation case, comparing raw and validated outputs across models on the same song and difficulty. Warnings assist human review; they do not rewrite gameplay content or imply that structural validation is a quality review.

### 3. Remove the ineffective beatmap output folder setting

- Remove the **Beatmap output folder** input and Browse action from Settings, along with its reset option. Update English and Traditional Chinese copy to explain that validated results live under managed `jobs/<job-id>/validated/` and can be opened from Jobs or History. Keep the temporary-files and osu! installation fields separate.
- Remove `outputPath` from new frontend/backend settings types, persistence, export/import, and diagnostics. Safely ignore the field in older stored settings and exported JSON without rejecting other settings or treating that path as the artifact location.
- Preserve existing jobs and history. Do not automatically delete an old `outputs` directory during migration. Distinguish the legacy `AppPaths.outputs` directory from the actual worker output, and remove obsolete directory creation or API fields only after checking other consumers.

## Acceptance

1. V30, V31, V32-mini, and V32 can each be installed on demand and pass loading, one- and multi-difficulty generation, validation, osu! import, and retry on supported Windows/NVIDIA hardware. GPU-free contract tests cover missing, corrupt, and mismatched models plus legacy jobs.
2. The same song and difficulty can produce separate, comparable jobs with different models. The known gap is flagged for human review. Record each model's warnings, time, and VRAM without assuming one model is better.
3. Changing or importing an old `outputPath` cannot change where new artifacts are written. Jobs and History reveal the actual managed result. Older settings and existing results survive upgrade; new settings exports omit the ineffective field.
4. Update bilingual guidance, the model compatibility matrix, third-party notices, and release tests. Installation and update acceptance continue under the release-candidate runbook.

## Outside this version

LoRA, arbitrary user checkpoints, taiko/catch/mania, AMD/Linux, remote workers, and automatic gameplay-quality repair. Models beyond V30/V31/V32-mini/V32 can be added in a later application version after their own compatibility and hardware acceptance.
